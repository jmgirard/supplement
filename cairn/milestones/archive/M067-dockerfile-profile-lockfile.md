# M067: Write Dockerfiles from profile lockfiles

**Status:** done (2026-10-27, PR #68 https://github.com/jmgirard/supplement/pull/68)

**Goal:** `write_dockerfile()` builds its image from the lockfile of the renv profile that renv picks for the site, and the image restores and renders with that profile active.

**Outcome:** `dockerfile_lock_source()` in `R/write-dockerfile.R` takes the lockfile from `lock_source()` (M066). It refuses a profile name outside `[A-Za-z0-9._-]`, or one that starts with `.`, and an unreadable `renv/profile`, with the new class `supplement_error_profile`. The name check runs before any check of a path built from the name. `read_lockfile_versions()` takes the picked path. `listed_exactly()` requires each part of `renv/profiles/<name>/renv.lock` to be listed with its exact letter case, else `supplement_error_no_file` with a rename hint. A file link to a missing lockfile is refused on Windows too. The lockfile hints name the profile. With a profile, `.dockerignore` is `*` and `!renv/profiles/<name>/renv.lock`, and the Dockerfile adds `RENV_PROFILE=<name>` to its `ENV` and copies the lockfile to the same path under `/opt/renv`. Without a profile the bytes are unchanged. The "Picked" message moved into `inform_lock_source()`, which `check_renv_lock()` and `write_dockerfile()` share. The help, GUIDE.md, README.md, NEWS.md, and DESIGN.md describe it. The tests add 9 cases, and a second gated Docker test builds and renders a site whose only lockfile is a profile's.

**Decisions:** none promoted. The plan chose `ENV RENV_PROFILE` with the lockfile at its profile path over copying it as a plain `renv.lock`, because renv keeps a profile's library under a profile prefix. It chose a new error class over reusing `supplement_error_lockfile`.
